# Signing and notarizing Liu for macOS

Gatekeeper opens a downloaded app without any prompt only when **all three** of
these hold:

1. the app is signed with a **Developer ID Application** certificate,
2. it is signed with the **hardened runtime** and a **secure timestamp**,
3. Apple's **notary service** has approved it and the resulting **ticket is
   stapled** into the artifact.

`scripts/package_macos_dmg.sh` does 2 and 3 by itself. This document covers the
Apple-side setup that produces the credentials it needs.

An ad-hoc signature (the fallback when no identity is present) can never be
notarized — it has no team identity for Apple to attribute the build to.

---

## 1. Developer ID Application certificate

Requires a paid Apple Developer Program membership. **Only the Account Holder
can create a Developer ID certificate**, and the team is limited to a small
number of them — reuse the existing one rather than minting a new one per
machine.

Easiest path (Xcode does the CSR dance for you):

> Xcode → Settings → Accounts → select the team → **Manage Certificates…** →
> **+** → **Developer ID Application**

Manual path: developer.apple.com → Certificates, IDs & Profiles → Certificates →
**+** → Developer ID → Developer ID Application, upload a CSR generated by
Keychain Access (*Certificate Assistant → Request a Certificate From a
Certificate Authority*), download the `.cer`, double-click to install.

Verify it landed in the keychain, with its private key:

```bash
security find-identity -v -p codesigning
# ... "Developer ID Application: <Name> (<TEAMID>)"
```

If the identity is missing here, the private key is not paired with the
certificate — re-export from the Mac that created the CSR (see §3).

## 2. Notarization credentials

An **App Store Connect API key** is the credential to prefer: it does not expire
on password changes, is scoped, and — unlike `--password` — never puts a secret
on a command line where `ps` can read it.

> App Store Connect → **Users and Access** → **Integrations** → **App Store
> Connect API** → **+** → Access: *Developer*

Download the `AuthKey_<KEYID>.p8` — **Apple serves it exactly once**. Note the
**Key ID** and the **Issuer ID** shown above the key list.

Store it as a local keychain profile so day-to-day builds need no environment
variables:

```bash
xcrun notarytool store-credentials liu-notary \
    --key /path/to/AuthKey_XXXXXXXXXX.p8 \
    --key-id XXXXXXXXXX \
    --issuer aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee
```

(For an *Individual* key rather than a Team key, omit `--issuer`.)

Sanity-check the credential before relying on it in a release:

```bash
xcrun notarytool history --keychain-profile liu-notary
```

## 3. Build locally

With the certificate installed and the profile stored:

```bash
NOTARY_PROFILE=liu-notary ./scripts/package_macos_dmg.sh
```

The identity is auto-detected, so `CODESIGN_IDENTITY` only needs setting when the
keychain holds more than one Developer ID cert. The script prints the notary
verdict and finishes with an `spctl` assessment of both artifacts. What you want
to see:

```
  spctl: <path>/Liu.app: accepted
  spctl: source=Notarized Developer ID
```

`source=Notarized Developer ID` is the whole point — `source=Developer ID`
(without "Notarized") means the signature is fine but the ticket is missing, and
users would still get the warning.

Escape hatches: `NOTARIZE=0` skips notarization; `CODESIGN_IDENTITY=-` forces the
ad-hoc fallback.

Other accepted credential forms, in the order the script tries them:

| variables | source |
| --- | --- |
| `NOTARY_PROFILE` | `notarytool store-credentials` profile |
| `NOTARY_KEY`, `NOTARY_KEY_ID`, `NOTARY_ISSUER` | API key `.p8` on disk (issuer only for team keys) |
| `NOTARY_APPLE_ID`, `NOTARY_PASSWORD`, `NOTARY_TEAM_ID` | app-specific password from appleid.apple.com |

## 4. Releases

A release is signed on the release Mac and nowhere else: no certificate, key or
password is stored on GitHub, and `.github/workflows/release.yml` only builds
the Linux packages. `scripts/release.sh` signs with the identity in the login
keychain and notarizes with the `liu-notary` profile above; it refuses an
ad-hoc identity or a missing profile, and checks that both macOS DMGs carry the
identity's signature and a stapled ticket. Its header has the whole order.

Once the profile is stored, the `.p8` belongs in an encrypted backup and not on
the disk: App Store Connect serves it once, so the backup is its only other
copy. Back up the Developer ID identity the same way — Keychain Access →
right-click the **Developer ID Application** identity → *Export…* → `.p12` with
a password. Export the **identity** (the disclosure triangle item that carries
the private key), not the bare certificate row — a `.p12` without the private
key imports cleanly and then fails at `codesign` with "no identity found".

## 5. What ships in each artifact

- **`Liu-<version>-<arch>.dmg`** — human download. Signed, notarized, stapled as
  its own container; the `Liu.app` inside is independently stapled.
- **`Liu-<version>-<arch>.zip`** — the auto-updater channel. Produced *after*
  stapling, so the ticket travels with it. This ordering is load-bearing: a zip
  made before stapling installs an app that Gatekeeper re-checks online, which
  fails offline and on first launch.

## Gotchas

- **`get-task-allow` must not be in the entitlements.** It is a debug-only
  entitlement and the notary service rejects any binary carrying it. The
  entitlements plist in the packaging script deliberately contains only
  `com.apple.security.device.audio-input`.
- **Never sign with `--deep`.** It would stamp the app's identifier and mic
  entitlement onto the nested `liu-notify` helper, which notarization rejects.
  The script signs inside-out instead: shader libs, then the helper with its own
  identifier, then the bundle.
- **Notarize the app *and* the DMG.** They are separate distributable containers
  and Gatekeeper assesses whichever one the user double-clicks.
- **Certificates expire (5 years), API keys do not.** An expired cert does not
  retroactively invalidate shipped builds — the secure timestamp proves the
  signature was made while it was valid — but it does block new releases.
- **Hardened runtime and child processes.** Liu spawns shells through a PTY;
  the hardened runtime does not restrict that, and each child runs under its own
  signature. What *is* affected is TCC: file-access prompts a child triggers are
  attributed to `Liu.app`, so users grant Full Disk Access to Liu itself.
